# MR 书法康养应用软件开发计划书

> 计划版本：v0.3  
> 更新日期：2026-06-10  
> 适用仓库：`eistinlandfrank/mr-calligraphy-cube-scene`  
> 文档定位：本计划书只描述 **MR 应用软件开发**，不包含硬件胶囊仓制造、工业设计效果图、实体产品结构、材料工艺、供应链或 3D 模型建模生产。

---

## 1. 项目目标

本项目要开发的是一个可长期迭代的 MR 书法康养应用，而不是一次性视觉展示页面。

系统由两个软件端组成：

1. **前台演示端**  
   用于展示老人进入沉浸式书法康养空间后的真实软件体验。前台需要具备可交互流程、真实状态变化、可记录练习数据、可生成报告的能力。

2. **后台编辑端**  
   用于编辑前台所使用的 3D 场景、空间 UI、交互热点、流程节点、书法练习内容和演示数据。后台编辑结果应能保存为配置，并被前台读取。

最终目标是形成一个数据驱动的软件系统：

```text
后台编辑配置 → 保存场景与流程 → 前台读取配置 → 用户真实交互 → 记录行为数据 → 生成学习报告
```

## 3. 当前项目基础

当前仓库已有一个本地 MR 书法 3D 交互网页原型，具备以下基础能力：

- 纯 HTML、CSS、JavaScript 本地运行。
- WebGL 立方体房间。
- 六面 cube 贴图。
- 10 个学习步骤。
- 键盘切换、底部导航、热点跳转。
- 场景角色配置。
- 页面内场景编辑面板。
- 本地 localStorage 保存。

这些能力适合作为早期原型基础，但后续需要重构为现代前端架构，使前台、后台、场景渲染、状态机和数据配置相互解耦。

## 4. 核心问题与改造方向

### 4.1 当前问题

| 问题 | 影响 | 改造方向 |
|---|---|---|
| 前台很多功能是静态展示 | 看起来像演示图，不像真实软件 | 引入状态机、真实交互和数据记录 |
| 场景数据大量写在代码中 | 后期维护困难 | 改为 JSON 配置驱动 |
| 编辑面板与演示页面混在一起 | 展示不专业，后台能力有限 | 拆分前台 `/demo` 与后台 `/admin` |
| 书法评分是固定文本 | 缺少真实产品可信度 | 建立路径跟随与评分算法 |
| 护工端只是视觉概念 | B 端软件逻辑不完整 | 护工端读取统一 session 状态 |
| 本地保存能力有限 | 长期开发难追踪版本 | 引入 IndexedDB 和导入导出 |

### 4.2 改造目标

- 前台由“展示页面”升级为“真实交互 Demo”。
- 后台由“临时编辑面板”升级为“3D 场景编辑器”。
- 书法练习由“展示图片”升级为“可操作游戏”。
- 评分反馈由“固定分数”升级为“算法计算”。
- 护工端由“静态面板”升级为“状态联动控制台”。
- 场景内容由“硬编码”升级为“配置驱动”。

## 5. 推荐技术路线

第一阶段推荐使用：

```text
Vite + React + Three.js + @react-three/fiber + Zustand + IndexedDB
```

### 5.1 技术选型说明

| 技术 | 用途 |
|---|---|
| Vite | 项目构建与本地开发服务 |
| React | 前后台 UI 组件化 |
| Three.js | 3D 场景、模型、灯光、相机、材质 |
| @react-three/fiber | 将 Three.js 组件化，便于编辑器复用 |
| Zustand | 管理场景状态、流程状态、编辑状态 |
| IndexedDB | 本地保存场景、流程、练习记录和版本 |
| JSON Schema | 校验场景配置与流程配置 |

### 5.2 运行策略

第一阶段优先保证桌面浏览器稳定运行：

- 鼠标拖拽视角。
- 鼠标 / 触控完成书法路径跟随。
- 键盘快捷操作。
- 凝视交互模拟。
- 护工端与老人端状态联动。

WebXR 作为增强能力放到后续阶段，不影响基础 Demo 展示。

## 8. 前台演示端功能规划

### 8.1 前台视角

前台包含三种视角：

1. **产品视角**  
   用于展示 MR 应用在沉浸胶囊场景中的整体运行效果。

2. **老人视角**  
   模拟老人看到的沉浸式书法空间。老人端不显示后台编辑控件，也不显示外部护工操作界面。

3. **护工视角**  
   显示护工对体验过程的监护与控制，包括当前阶段、剩余时间、暂停状态、练习完成度和安全提示。

### 8.2 真实流程状态机

前台流程由状态机驱动。

```text
idle
  ↓
ready_check
  ↓
enter_experience
  ↓
immersive_intro
  ↓
calligraphy_tutorial
  ↓
practice_game
  ↓
scoring
  ↓
report
  ↓
caregiver_confirm
  ↓
finished
```

每个状态需要包含：

- 状态 ID。
- 状态标题。
- 状态说明。
- 允许操作。
- 默认下一状态。
- 进入状态时触发的动作。
- 离开状态时保存的数据。

### 8.3 前台真实化要求

| 功能 | 真实化要求 |
|---|---|
| 开始体验 | 创建 session，进入状态机 |
| 暂停体验 | 停止计时器、动画和输入采集 |
| 继续体验 | 恢复计时器、动画和输入采集 |
| 结束体验 | 保存 session，进入报告页 |
| 书法练习 | 记录用户轨迹点 |
| 评分 | 根据轨迹和行为计算 |
| 报告 | 根据 session 数据生成 |
| 护工操作 | 与老人端实时同步 |
| 数据面板 | 显示真实 session 状态或明确标注模拟数据 |

## 9. 书法游戏模块规划

第一阶段只实现一个核心游戏：**永字八法路径跟随**。

### 9.1 用户操作

用户通过鼠标、触控或后续 XR 输入沿着标准路径描摹“永”字笔画。

### 9.2 系统记录

系统记录：

- 用户轨迹点。
- 每一笔开始时间。
- 每一笔结束时间。
- 是否按顺序完成。
- 偏离标准路径的距离。
- 暂停次数。
- 重写次数。

### 9.3 评分维度

```text
综合分 = 路径准确度 40% + 笔顺完成度 25% + 节奏稳定度 20% + 中断控制 15%
```

报告输出：

- 路径准确度。
- 笔顺完成度。
- 节奏稳定度。
- 专注度。
- 练习建议。

## 10. 护工端功能规划

护工端需要读取统一 session 状态，而不是单独写一套假数据。

### 10.1 护工端显示

- 当前体验阶段。
- 当前练习字。
- 当前笔画。
- 体验剩余时间。
- 暂停状态。
- 完成度。
- 老人端是否请求帮助。
- 模拟心率。
- 模拟呼吸。
- 系统安全状态。

### 10.2 护工端操作

- 暂停。
- 继续。
- 结束体验。
- 重置当前练习。
- 呼叫老人端。
- 切换放松模式。

### 10.3 模拟数据规则

健康类数据第一阶段可以模拟，但必须由流程状态驱动，并在界面标注“模拟数据”。

示例：

- 沉浸导入阶段：心率缓慢下降。
- 练习阶段：心率轻微上升。
- 暂停阶段：数据冻结。
- 报告阶段：显示本次平均值。

## 15. 长期开发管理方式

本项目按长期开发管理，不把任务写成一次性开发说明。

所有开发任务统一记录在：

```text
docs/implementation-checklist.md
```

执行规则：

1. 每个任务都有唯一编号。
2. 每完成一项，将 `- [ ]` 改为 `- [x]`。
3. 每次只勾选已经完成并通过验收的任务。
4. 如果任务部分完成，不勾选，只在任务下方添加进度说明。
5. 如果发现新任务，添加到对应阶段，不直接打乱原编号。
6. 每次提交应说明完成了哪些任务编号。
7. 开发计划书只维护方向、架构和标准；具体执行进度维护在清单文件里。

## 17. MVP 验收标准

第一版 MVP 完成时，应满足：

- 前台有真实状态机。
- 前台按钮会改变状态和数据。
- 书法游戏可操作。
- 系统能记录用户轨迹。
- 评分由算法计算。
- 报告由 session 数据生成。
- 护工端能控制老人端流程。
- 后台可以编辑 3D 对象属性。
- 后台可以保存配置。
- 前台可以读取后台配置。
- 支持 JSON 导入导出。
- 不支持 WebXR 时仍可桌面演示。

## 18. 结论

本项目下一阶段的重点不是继续增加静态视觉效果，而是把当前原型升级成一个可长期开发、可维护、可真实交互的软件系统。

核心路线是：

```text
真实交互流程 + 数据驱动场景 + 后台编辑能力 + 可追踪任务清单
```

开发计划书负责说明方向和架构；执行进度由 `docs/implementation-checklist.md` 跟踪。
