# MR 书法康养舱真实应用软件开发计划书

> 版本：v1.0  
> 项目性质：面向养老院 B 端落地使用的 MR 书法康养舱软件系统  
> 重要修正：本计划不再以“演示项目”“1-10 步骤展示页”为目标，而是以**可真实运行、可接设备、可服务多位老人轮换使用**的软件产品为目标。  
> 范围说明：本文只描述软件系统开发，不包含舱体工业设计、材料工艺、实体结构制造、3D 模型建模生产。

---

## 1. 项目重新定位

当前项目应从“MR 书法场景演示网页”升级为：

# 面向养老院的 MR 书法康养舱应用系统

系统部署在养老院的沉浸式书法康养舱中，服务真实使用场景：老人由护工协助进入舱体，舱门关闭后，老人通过舱内沉浸屏幕、语音、凝视、扶手按钮或轻手势完成书法康养体验；护工在舱外通过舱体控制屏监看状态、控制流程、处理异常；系统自动保存练习记录、生成作品与报告，并将设备恢复到下一位老人可使用状态。

该系统不是 PPT 演示，也不是单纯 3D 展示页面，而是一套包含运行端、护工端、后台端和设备通信层的真实应用软件。

## 2. 核心用户与使用环境

### 2.1 用户角色

| 角色 | 真实需求 | 软件对应端 |
|---|---|---|
| 老人 | 安全、简单、沉浸、可完成书法体验 | 舱内运行端 Capsule Runtime |
| 护工 | 协助入舱、启动课程、查看状态、处理异常 | 舱外护工控制端 Operator Console |
| 养老院活动管理员 | 管理课程、查看记录、安排活动 | 管理后台 Admin Console |
| 内容维护者 | 更新书法课程、场景、引导语、作品模板 | 内容配置后台 Content Studio |
| 设备维护人员 | 查看舱体状态、故障、日志、版本 | 设备运维后台 Device Admin |

### 2.2 使用环境

- 养老院活动室
- 康养中心
- 日间照料中心
- 老年大学书法活动空间

### 2.3 真实使用约束

- 老人不应看到复杂菜单。
- 护工必须能随时接管。
- 舱体必须支持一键停止和安全开舱。
- 系统必须支持连续多人轮换使用。
- 系统应支持本地局域网运行，即使外网不可用也能完成基本体验。
- 健康数据若未接真实设备，必须标注为模拟或体验状态，不得冒充医疗数据。

## 3. 软件系统组成

真实产品应拆成五个软件层级。

### 3.1 舱内运行端 Capsule Runtime

部署在 MR 舱内主机上，负责老人看到和体验的内容。

核心能力：

- 启动沉浸式水墨空间。
- 加载书法课程。
- 播放引导语与环境音。
- 呈现虚拟书法笔画。
- 采集老人交互输入。
- 记录书写轨迹。
- 生成即时反馈。
- 响应护工端暂停、继续、退出指令。
- 在紧急状态下立即进入安全界面。

### 3.2 舱外护工控制端 Operator Console

部署在舱体外置控制屏上，不是平板，不是手机。

核心能力：

- 选择老人档案。
- 选择课程。
- 启动体验。
- 控制舱门打开 / 关闭。
- 查看舱门、座椅、通风、屏幕、音量状态。
- 查看当前体验阶段。
- 查看书法练习进度。
- 暂停、继续、结束体验。
- 接收老人求助。
- 触发安全退出。
- 查看本次体验报告。
- 确认设备清洁与复位。

### 3.3 管理后台 Admin Console

用于养老院活动管理员。

核心能力：

- 管理老人档案。
- 管理课程计划。
- 查看历史体验记录。
- 查看作品列表。
- 导出活动报告。
- 管理设备列表。
- 查看设备运行状态。

### 3.4 内容配置后台 Content Studio

用于维护书法内容和空间内容，不等同于“做模型”。

核心能力：

- 管理书法字库。
- 管理笔画路径。
- 管理课程脚本。
- 管理语音引导文案。
- 管理沉浸场景资源引用。
- 管理作品模板。
- 配置体验流程。
- 预览内容效果。

### 3.5 设备通信层 Device Bridge

用于把软件和真实舱体设备解耦。

核心能力：

- 舱门开关状态读取。
- 舱门开关指令下发。
- 紧急按钮状态读取。
- 通风状态读取与控制。
- 灯光亮度控制。
- 座椅角度读取与控制。
- 舱内屏幕状态读取。
- 音频状态控制。
- 设备错误上报。

第一阶段可以先实现 Device Simulator，后续接真实硬件接口。

## 4. 真实使用闭环

系统不再采用“1-10 展示步骤”。真实产品使用的是**Session 会话闭环**。

```text
活动预约
  ↓
护工选择老人和课程
  ↓
设备自检
  ↓
开舱与入舱辅助
  ↓
老人入座与安全确认
  ↓
舱门关闭
  ↓
沉浸式书法体验
  ↓
书法交互与数据采集
  ↓
系统评分与作品生成
  ↓
护工查看报告
  ↓
舱门打开
  ↓
离舱与清洁复位
  ↓
设备进入下一位可用状态
```

每一次体验都生成一个 Session，而不是一次视觉展示。

## 5. Session 状态机

系统核心是可追踪、可暂停、可恢复、可异常处理的 Session 状态机。

### 5.1 状态定义

```text
scheduled            已预约
idle                 设备空闲
self_check           设备自检
ready_for_entry      准备入舱
door_opening         舱门打开中
waiting_entry        等待老人入舱
seat_adjusting       座椅调整
safety_confirm       安全确认
curtain_closing      舱门关闭中
immersive_booting    沉浸环境启动
intro_guidance       呼吸与课程导入
calligraphy_guidance 笔画示范
writing_active       书法体验进行中
paused               暂停
help_requested       老人求助
emergency_stop       紧急停止
scoring              评分生成
artwork_generated    作品生成
report_review        护工查看报告
door_opening_exit    结束开舱
cleaning_required    待清洁
resetting            系统复位
ready_next           下一位可用
```

### 5.2 状态机要求

- 每个状态必须可记录进入时间和退出时间。
- 每个状态必须定义允许的操作。
- 护工端和老人端必须读取同一个 Session 状态。
- 任何状态下紧急停止优先级最高。
- 外部设备状态与软件状态不一致时，系统必须进入安全检查状态。

## 6. 关键业务功能

### 6.1 设备自检

开始体验前，系统必须检查：

- 舱门是否可控。
- 紧急按钮是否在线。
- 舱内屏幕是否正常。
- 音频是否正常。
- 通风是否正常。
- 座椅是否处于可调范围。
- 当前舱体是否已清洁复位。

自检未通过时，护工端不能启动体验。

### 6.2 入舱辅助

护工端控制舱门向上打开。系统进入 `waiting_entry` 状态。

软件需要显示：

- 入舱提示。
- 座椅状态。
- 舱门状态。
- 安全确认按钮。

### 6.3 舱门控制

舱门逻辑：

- 开门：向上打开。
- 关门：向下闭合。
- 关闭过程中检测阻挡。
- 关闭后进入锁定状态。
- 紧急情况下立即停止运动，并允许人工开舱。

软件不直接操作电机，而是通过 Device Bridge 调用接口。

### 6.4 舱内沉浸体验

老人端只看到舱内沉浸内容，不显示外部环境和复杂系统信息。

核心内容：

- 水墨空间。
- 呼吸引导。
- 今日练习字。
- 笔画示范。
- 虚拟书写。
- 柔和鼓励反馈。
- 作品生成。

### 6.5 书法交互

第一阶段使用可实现的交互方式：

- 鼠标 / 触控模拟。
- 舱内按钮模拟。
- 凝视模拟。
- 键盘快捷键用于测试。

后续接入：

- 手势摄像头。
- 红外追踪。
- 深度摄像头。
- 扶手控制按钮。

### 6.6 评分与报告

评分必须由练习数据生成。

输入数据：

- 笔画完成度。
- 笔顺正确率。
- 路径偏差。
- 节奏稳定度。
- 暂停次数。
- 求助次数。
- 完成时长。

输出报告：

- 完成作品。
- 本次练习字。
- 综合完成度。
- 节奏状态。
- 专注状态。
- 下次推荐。

### 6.7 清洁与复位

体验结束后，系统进入 `cleaning_required`，护工确认清洁后才进入 `ready_next`。

软件需要记录：

- 本次结束时间。
- 清洁确认人。
- 设备复位状态。
- 下一次可用状态。

## 7. 技术架构

### 7.1 推荐总体架构

```text
apps/
  capsule-runtime/       舱内运行端
  operator-console/      舱外护工控制端
  admin-console/         养老院管理后台
  content-studio/        书法内容配置后台

services/
  api-server/            业务 API
  device-bridge/         设备通信服务
  session-engine/        Session 状态机服务
  scoring-engine/        书法评分服务
  report-engine/         报告生成服务

packages/
  ui/                    共享 UI 组件
  scene-core/            3D / MR 场景核心
  calligraphy-core/      书法路径与评分核心
  device-protocol/       设备协议定义
  data-schema/           数据结构与校验
```

### 7.2 第一阶段技术栈

| 层级 | 技术 |
|---|---|
| 前端 | Vite + React + TypeScript |
| 3D / MR | Three.js + @react-three/fiber |
| 状态管理 | Zustand 或 XState |
| 本地数据库 | SQLite 或 IndexedDB |
| 后端 API | Node.js + Fastify / Express |
| 实时通信 | WebSocket |
| 数据校验 | Zod / JSON Schema |
| 设备模拟 | Device Simulator |

### 7.3 为什么需要后端

真实使用项目不能只靠浏览器本地状态，因为需要：

- 保存多个老人档案。
- 保存多次体验记录。
- 护工端和老人端同步状态。
- 记录设备状态。
- 生成长期报告。
- 管理多台设备。
- 支持局域网部署。

第一阶段可以使用本地 Edge Server，运行在同一台主机或养老院局域网服务器中。

## 9. 设备接口设计

真实项目必须先定义设备接口，再决定接真实硬件还是模拟硬件。

### 9.1 Device Bridge API

```text
GET  /device/status
POST /device/door/open
POST /device/door/close
POST /device/door/stop
POST /device/light/set
POST /device/ventilation/set
POST /device/seat/set-angle
POST /device/audio/set-volume
GET  /device/emergency-stop
POST /device/reset
```

### 9.2 WebSocket 事件

```text
device.status.changed
device.door.opening
device.door.opened
device.door.closing
device.door.closed
device.door.blocked
device.emergency.pressed
session.state.changed
session.help.requested
session.report.generated
```

### 9.3 第一阶段设备模拟器

第一阶段必须先实现 Device Simulator：

- 模拟舱门打开。
- 模拟舱门关闭。
- 模拟紧急停止。
- 模拟通风状态。
- 模拟座椅角度。
- 模拟屏幕在线。

这样前后端可以先真实联动，后续再替换为真实设备驱动。

## 10. 前端应用要求

### 10.1 Capsule Runtime

舱内端要求：

- 全屏运行。
- 禁止显示浏览器调试 UI。
- 支持自动恢复到当前 Session。
- 护工端暂停时立即进入暂停界面。
- 紧急停止时立即停止交互并提示等待护工。
- 体验结束后显示作品生成动画。

### 10.2 Operator Console

护工端要求：

- 大按钮。
- 高对比。
- 明确状态。
- 不允许误触危险操作。
- 结束、开舱、紧急操作需要二次确认。
- 与舱内端实时同步。

### 10.3 Admin Console

管理后台要求：

- 管理老人档案。
- 管理课程。
- 查看历史报告。
- 查看设备状态。
- 导出活动数据。

### 10.4 Content Studio

内容后台要求：

- 配置课程脚本。
- 配置笔画路径。
- 配置引导语。
- 配置沉浸场景资源。
- 配置作品模板。
- 发布课程版本。

## 11. 开发阶段

### R0：现有项目清理

目标：停止继续围绕“1-10 展示步骤”开发，将其保留为 legacy。

### R1：真实产品架构搭建

目标：建立多应用、多服务、共享包的工程结构。

### R2：Session 状态机

目标：实现真实会话流程和状态同步。

### R3：设备模拟器与 Device Bridge

目标：让舱门、通风、座椅、急停等能力先通过模拟器真实联动。

### R4：舱内运行端

目标：实现老人端沉浸体验、书法练习、作品生成。

### R5：护工控制端

目标：实现护工外部监看、控制、异常处理。

### R6：书法引擎与评分

目标：实现笔画路径、轨迹采集、评分、报告。

### R7：后台与内容配置

目标：实现老人档案、课程、设备、内容发布。

### R8：数据持久化与报告

目标：记录真实使用数据，形成历史记录和可导出报告。

### R9：联调与部署

目标：形成可在本地或养老院局域网运行的版本。

## 12. MVP 定义

第一版可用 MVP 不要求接真实硬件，但必须像真实系统一样运行。

MVP 必须做到：

- 舱内端和护工端分离。
- 护工端可以启动一次 Session。
- 设备模拟器可以控制舱门开关状态。
- 舱门开关状态影响 Session 流程。
- 老人端可以完成一次“永”字书法体验。
- 系统能记录练习轨迹。
- 系统能生成作品和报告。
- 护工端能查看报告。
- 体验结束后进入清洁复位流程。
- 系统恢复到下一位可用状态。

如果只是点击 1-10 页面切换，不算 MVP。

## 13. 质量标准

### 13.1 真实可用标准

- 所有关键按钮必须触发真实状态变化。
- 所有报告必须来自 Session 数据。
- 所有设备状态必须来自 Device Bridge 或 Simulator。
- 护工端和老人端必须实时同步。
- 系统必须能连续完成至少 3 次 Session。

### 13.2 安全标准

- 任意状态可紧急停止。
- 舱门动作可中止。
- 结束体验不可直接丢失数据。
- 异常断开后可恢复 Session。
- 老人端始终有“呼叫护工”入口。

### 13.3 产品标准

- 老人端简洁、低刺激。
- 护工端清楚、高效、可控。
- 管理端适合批量查看记录。
- 内容端可以更新课程。

长期执行清单放在：

3. 部分完成不得勾选。
4. 每次提交说明应包含完成的任务编号。
5. 新增任务只能追加，不能随意改旧编号含义。
6. 开发计划书只维护系统方向，执行清单维护开发进度。

## 15. 结论

项目方向应彻底从“演示型 MR 网页”改为“真实可运行的 MR 书法康养舱应用系统”。

真正的核心不是多视角渲染，也不是 1-10 流程展示，而是：

```text
真实舱体状态
+ 真实 Session 流程
+ 舱内老人端
+ 舱外护工端
+ 设备通信层
+ 书法交互数据
+ 报告与复位闭环
```

只有这些部分跑起来，这个项目才像一个能真实使用的产品。
